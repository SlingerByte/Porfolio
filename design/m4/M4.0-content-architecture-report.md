## 2. Project Candidate Matrix

No hay proyectos candidatos que clasificar todavía. La matriz queda definida como **plantilla de evaluación** para cuando el usuario los entregue:

| Campo | Qué se pide |
|---|---|
| nombre / descripción | tal como existe hoy |
| problema que resuelve | 1 línea, lenguaje humano |
| rol del autor | solo / equipo (¿qué parte hizo él?) |
| tecnologías | stack real, no aspiracional |
| estado | live / archived / WIP |
| impacto/resultados | métricas si existen (usuarios, benchmarks, tests) |
| repo / demo | URLs funcionando |
| screenshots/assets | disponibles o no |
| evidencia técnica | tests, docs, README calidad, arquitectura |

**Criterios de clasificación** (en este orden):

1. **Evidencia real verificable** (repo público con commits propios > demo caída > "lo tengo privado").
2. **Relevancia AI/dev** (integra LLMs/RAG/datos/automatización = diferenciador para el posicionamiento).
3. **Variedad técnica** entre los seleccionados (no 4 CRUDs iguales).
4. **Claridad para recruiter** (explicable en 2 frases).
5. Polimento percibido.

Clasificación tentativa una vez existan candidatos:
- **PRIMARY (máx 3):** evidencia + relevancia AI + variedad.
- **SECONDARY (1–2):** sólidos pero redundantes o sin demo.
- **OPTIONAL:** mencionables en About sin card propia.
- **EXCLUDE:** tutoriales-followed, dead links, sin rol propio.

⚠️ Regla anti-inflado (M0.1): **3 proyectos pulidos > 8 a medias.**

## 3. Professional Narrative

**Pregunta:** ¿qué debe entender un recruiter tras 30–60 segundos?

### Frase central propuesta (hipótesis a validar con datos del usuario)

> *"Desarrollador junior que construye aplicaciones web completas y las hace más inteligentes integrando IA de forma práctica — y que demuestra cada afirmación con código visible."*

### Mensajes secundarios propuestos

1. **Qué construye:** productos web end-to-end (frontend React/TS + backend/API).
2. **Diferenciador:** integra AI/LLMs donde resuelven un problema real, no como gimmick (el objeto AI signature de la escena refuerza esto visualmente).
3. **Cómo trabaja:** código limpio, versionado, testeado — evidenciable por repos.
4. **Base formal:** educación/certificaciones en progreso (a confirmar).
5. **Hacia dónde evoluciona:** especialización AI-engineering aplicada a producto.

Estos mensajes son **hipótesis estructurales**: se confirman o corrigen cuando existan los proyectos reales.

## 4. Information Architecture

Mantiene la IA consolidada del reporte Fase-0 (5 destinos, anti-inflado), ahora mapeada al contenido confirmado:

| Sección | Contenido | Racional |
|---|---|---|
| **Hero** | Nombre + titular (frase central) + CTA único (ver trabajo / contacto) | 3 elementos máximo; la lámpara ya carga la narrativa visual |
| **Work** | 3–4 project cards (PRIMARY primero) + link a GitHub como "el resto" | desk/monitor de la escena |
| **About** | 2–3 párrafos: quién es, qué le mueve hacia AI, contexto personal ligero (los gatos existen 😉) | shelf |
| **Experience** | Timeline compacta fusionada: empleos/prácticas/freelance + education + certs JUNTOS | evita sección-CV interminable |
| **Skills** | 4–5 grupos máx (Languages / Frameworks / AI & Data / Tooling / Soft) | corkboard |
| **Contact** | email + GitHub + LinkedIn + CV download. Sin formulario backend (SPA sin server) | door |

**Fusiones decididas:** Education/Certs dentro de Experience · Skills dentro del bloque About-corkboard narrativo pero con UI propia mínima. **Sobra:** ninguna sección extra (no blog, no testimonials hasta tenerlos reales).

## 8. Recruiter Evaluation

| Perfil | Busca primero | Riesgo detectado | Mitigación |
|---|---|---|---|
| **Recruiter técnico** | Repos, stack real, calidad de commits, tests | Portfolio bonito sin evidencia = descarte inmediato | Links a repo SIEMPRE visibles en cards; stack explícito por keywords |
| **Recruiter generalista** | Entender qué hace y para qué sirve en <30s | La metáfora 3D puede oscurecer el mensaje | Regla ya implementada: nav HTML permanente + contenido DOM accesible sin WebGL; titulares autocontenidos |
| **Hiring manager** | Evidencia de juicio técnico: decisiones, trade-offs, AI aplicada con criterio | Junior sin casos de decisión documentada | 1 párrafo "por qué lo construí así" por proyecto PRIMARY (en card expandida o repo README) |

**Problema de comunicación identificado:** el mayor riesgo del concepto no es técnico sino narrativo — *que la experiencia supere a la información*. Las contramedidas ya están en la arquitectura (nav siempre visible, skip intro, fallback classic); la que falta es disciplina de contenido: cada sección debe poder leerse sola, sin haber visto la escena.

## 9. Content/Performance Constraints

Con escena en ~104 draw calls / ~29k tris / 283 KB gz (lazy) + 63 KB gz DOM inicial:

| Límite propuesto | Valor | Justificación |
|---|---|---|
| Project cards visibles | **3–4** (+ link externo al resto) | jerarquía y presupuesto visual |
| Peso imagen/card | ≤ 250 KB WebP, lazy-loaded | presupuesto global de assets <1.5MB ya fijado |
| Assets totales de contenido | ≤ 12 archivos (~1.2 MB) | coexiste con chunk escena en mobile |
| Longitud textos | summary ≤160 chars · about ≤900 chars · case-study expandido opcional fuera del critical path | legibilidad sobre scrim + pixel rendering |
| Fuentes | ya self-hosted ~40KB (Fraunces/Inter/Plex Mono subset) | cerrado |
| Móvil | cards full-screen, imágenes lazy, escena reducida según plan responsive previo | fase propia posterior |
